### concept: Espressif 4MB CircuitPython upgrade = TinyUF2 + ROM/esptool (two bootloaders)  `evidence-supported`

Three stacked images, not one “firmware”:

| Layer | What it is | How you talk to it |
|---|---|---|
| ESP32-S2 **ROM** bootloader | In silicon; cannot be erased | Hold **BOOT**, tap **RESET**, release BOOT. No USB drive. `esptool` on the CDC port. |
| **TinyUF2** | UF2 USB bootloader in flash (Adafruit). Latest listed on board pages: **0.35.0** (2026-09-11) | After TinyUF2 is installed: a `*BOOT` drive (this board: `BITS2BOOT`). Drag a `.uf2`. |
| **CircuitPython** | The Python firmware + `CIRCUITPY` filesystem | `.uf2` onto TinyUF2, **or** `.bin` via ROM/`esptool` (no UF2 needed for `.bin`) |

**4MB Espressif + CircuitPython 10:** TinyUF2 **≥ 0.33.0** so `ota_0` is **2816K** (the old `ota_0`+`ota_1` 1408K+1408K merged). **`ffat` / CIRCUITPY is 960K in both tables** (same offset `0x310000`). Combining OTA slots grows the **firmware** image, not CIRCUITPY. CIRCUITPY is not an OTA partition. Sources: TinyUF2 `partitions-4MB.csv` vs `partitions-4MB-noota.csv` (0.32.0 and 0.35.0); [Adafruit Learn CP10 4MB TinyUF2](https://learn.adafruit.com/adafruit-metro-esp32-s2/update-tinyuf2-bootloader-for-circuitpython-10-4mb-boards-only). BPI-Bit-S2 is ESP32-S2 **4MB flash / 2MB PSRAM**. TinyUF2 **< 0.33** cannot load a CP10 UF2 (firmware won’t fit `ota_0`); CIRCUITPY size is unchanged.

**Scope (do not over-generalize):** Adafruit TinyUF2 **4MB** tables only. Boards with **≥8MB** flash keep a large firmware slot and **skip** this TinyUF2 CP10 update path ([Adafruit Learn](https://learn.adafruit.com/adafruit-metro-esp32-s2/update-tinyuf2-bootloader-for-circuitpython-10-4mb-boards-only)). A vendor fork with a different partition CSV would differ; BPI-Bit-S2 ships Adafruit `tinyuf2-bpi_bit_s2-0.35.0`.

**esptool v5 (this Mac: 5.1.0 in `…/PythonVEs/MicroControllers`):** use `esptool` not `esptool.py`; commands hyphenated (`write-flash`, `erase-flash`, `chip-id`); `--verify` is gone (verify is automatic). Native-USB chips already in ROM mode: `--before no-reset`. Do **not** copy BananaPi Bit-S2 docs that say `--chip esp32s3` — this SoC is **esp32s2**.

**A CircuitPython `.uf2` does not update TinyUF2.** It only replaces the CP app partition. To bump TinyUF2 while already in `*BOOT` mode, drag `update-tinyuf2-<board>-0.35.0.uf2` (in the same GitHub zip) *then* the CP `.uf2`. `combined.bin` @ `0x0` via esptool is the ROM-mode reinstall and **wipes CIRCUITPY**. Same-layout CP `.uf2` with TinyUF2 already ≥0.33 **keeps the filesystem** — on-device 2026-09-11: UID `0740D10F1BE9` 10.0.3 → 10.3.0, TinyUF2 0.35.0, `code.py`/`lib` still ran. TinyUF2 **< 0.33** cannot load CP 10 on 4MB — update TinyUF2 first. Identify **each** board (`boot_out.txt` UID + `INFO_UF2.TXT`); SKU is not a version.

**BPI-Bit-S2 TinyUF2 entry (board page + BPI-Steam):** tap **RESET**, then tap **BOOT** within ~1 s when the matrix goes purple → `BITS2BOOT`. Adafruit “slow double-RESET” is the generic ESP32-S2 recipe; prefer the BPI sequence on this board.

Artifacts (verified HTTP 200 on 2026-09-11):

- CP 10.3.0 UF2: `https://downloads.circuitpython.org/bin/bpi_bit_s2/en_US/adafruit-circuitpython-bpi_bit_s2-en_US-10.3.0.uf2`
- TinyUF2 0.35.0 zip (`combined.bin` + `update-tinyuf2-bpi_bit_s2-0.35.0.uf2`): `https://github.com/adafruit/tinyuf2/releases/download/0.35.0/tinyuf2-bpi_bit_s2-0.35.0.zip`

**How-to-check-status:** board page “Latest version” for TinyUF2; `INFO_UF2.TXT` on the BOOT drive; `boot_out.txt` on CIRCUITPY for the CircuitPython version. CIRCUITPY **user** size ≠ TinyUF2 `Flash Size` (`Flash Size` = `ota_0`, 0x2C0000 / 2816K on CP10 4MB). Measure CIRCUITPY with `df -h /Volumes/CIRCUITPY` or `os.statvfs("/")`. `df` reports **less** than table/`diskutil` `ffat` (FAT overhead; this board ~941 KiB vs 983040 B). Prefer `diskutil` Disk Size or `os.statvfs` for comparison to the 960K table. UID `0740D10F1BE9`: FAT **983040 B** = table `ffat` 960K. Independent `ffat` ballpark: [circuitpython#6285](https://github.com/adafruit/circuitpython/issues/6285) QT Py ESP32-S2, CP 7.2.5, `os.statvfs` Size **963072**. CSV rows / arithmetic: sibling `tooling-4mb-partitions.md`.

### concept: two similarly-named "CircuitPython" extensions do different jobs — do not conflate  `evidence-supported`

- **Primary source, consult early for any `circuitpythonsync` question:** `/Users/alex/.cursor/extensions/padgettholdings.circuitpythonsync-2.2.2-universal/resources/helpfile.md` (its own "# Welcome to CircuitPython Sync" doc, bundled with the extension; also `resources/cptemplate*.txt` for its default project-template content). Alex's direction 2026-09-11, prompted by the `.circuitpyignore` correction below — a claim about this extension's behavior was persisted into this file without checking `helpfile.md` or `dist/extension.js` first, and turned out wrong. Check this file (and/or grep `dist/extension.js`) **before** answering or persisting any claim about what the extension does — don't rely on a prior session's memory of its behavior.
- **`padgettholdings.circuitpythonsync`** (v2.2.2, installed under **Cursor's own** extension dir `~/.cursor/extensions/`, not `~/.vscode/extensions/`) — the actual **file-sync tool**. Commands (Command Palette): `CP Copy Files to Board` / `CP Copy Libs to Board` / `CP Set Board from boot_out.txt` / `CP Select Board` / `CP Set Drive` / `CP Manage Files Copy` / `CP Compare file to board` / `CP Upload UF2 Firmware`, etc. Uses per-experiment `.vscode/cpfiles.txt` (explicit allowlist manifest for "Copy Files", supports `source -> /dest` mapping) — a repo file. **Its board/drive selection and version state are NOT in any repo file or `settings.json`** — grepped every `.vscode/settings.json` and the shared workspace file for `circuitpythonsync.*`, zero hits; that state lives in the extension's own internal storage, set interactively via its own commands only.
- **Correction 2026-09-11 (invalidates a same-day-earlier claim in this file):** `.circuitpyignore` is **not** a real mechanism of this extension — there is no ignore/exclude-file feature for "Copy Libs to Board" at all. Verified by grepping the extension's own `dist/extension.js` (2.2.2) for `circuitpyignore`/`circuitpy_ignore`/`ignoreFile`/`excludeFile` (all zero hits) and reading its bundled `resources/helpfile.md` § Library Support, which states plainly: "any CP compatible library can be used by copying the files/folders into the `lib` folder. Then the `Copy Libs to Board` command will copy the libraries to the board" — whole-folder copy, no filtering option, no mention of any ignore file anywhere in the docs or the `package.json` contributed settings. The earlier claim was recorded without checking source and was wrong. **Practical upshot:** the only two gates on what this extension ever writes to a board are (1) `cpfiles.txt`'s explicit allow-list (`Copy Files to Board`) and (2) `lib/`'s literal on-disk contents (`Copy Libs to Board`, unconditional whole-folder copy) — nothing else in a repo root is ever at risk regardless of any ignore-file convention. To keep dev cruft (e.g. pytest's `__pycache__/`) out of `lib/` before a Copy-Libs sync, stop it from being generated in the first place (`sys.dont_write_bytecode = True` in the host test's `conftest.py`, verified 2026-09-11 exp16) rather than trying to filter it at sync time.
- **`wmerkens.vscode-circuitpython-v2`** (installed under `~/.vscode/extensions/`) — a **different, unrelated** extension providing Pylance IntelliSense stubs + its own (separate, mostly-unused-here) serial monitor/board commands. Its settings **do** live in files, under the `circuitpython.*` key namespace (singular) — e.g. the shared `CircuitPy_VSCode.code-workspace`'s `circuitpython.board.version`, `circuitpython.bundle.*`, `python.analysis.extraPaths`. **These keys do not control file sync** — an easy mix-up since both extensions share the "circuitpython" name and this shared workspace file's comments ("Board-level CircuitPythonSync settings ... are defined in the workspace file") are misleadingly worded as if they did.
- **Practical upshot:** the "shared CircuitPythonSync edit" escalation concern in this project's working notes is about the *sync extension's* board/drive selection (an interactive, per-command action only Alex can do — no file to edit, hence no way for an agent to touch it even unintentionally) — not about the `wmerkens` workspace-level `circuitpython.*` keys (which are a Pylance-only concern, lower stakes).
- **AI-agent capability boundary (worth restating, not project-specific):** no available tool invokes VS Code/Cursor's Command Palette or an extension's registered commands. Anything gated behind a `CP …` command must be run by the human; an agent's alternative is a direct filesystem operation on the mounted CIRCUITPY volume (same destructive-ops gate as any other on-device write) — which reproduces the *effect* for simple cases but skips the extension's own `.circuitpyignore` handling, hash-diffing, and backup-manifest bookkeeping. Discovered 2026-09-11, exp16, investigating why per-experiment `settings.json` files didn't contain the sync config the source-code comments implied.

**`padgettholdings.circuitpythonsync` is not multi-root-workspace-aware — hardcoded to `workspaceFolders[0]`.** Verified by reading `dist/extension.js` (v2.2.2) directly: every file-existence check for "Copy Files to Board" / "Copy Libs to Board", the `cpfiles.txt` manifest read, and its file-system watchers use `workspace.workspaceFolders[0]` (the first folder in whatever multi-root window is currently open) — **32** occurrences, **zero** uses of `getWorkspaceFolder` (the API that would resolve "which folder does this file belong to"). In this repo's multi-experiment window, whichever experiment happens to sit at folder-index 0 is the *only* one these two commands will work correctly for; every other open experiment's "Copy Files to Board" will fail with `"!! No files specified to copy exist !!"` even when that experiment's own `.vscode/cpfiles.txt` + `code.py` are perfectly set up — because the extension is checking the *wrong* folder's manifest/files, not the focused one. **Fix (no shared-file edit needed):** open the target experiment alone in its own window (`File → Open Folder`) when running these two commands; `workspaceFolders[0]` then trivially resolves to it. Reordering the shared multi-root workspace's folder list instead "fixes" one experiment but breaks whichever was previously at index 0. Discovered 2026-09-11 (exp16, Alex hit the error; traced to source rather than trial-and-error). A local script that bypasses the extension (e.g. exp16 `scripts/sync_files_to_board.py`) is unaffected by this bug. **Remediation verified 2026-09-11**: Alex manually reordered the multi-root workspace folder list (Exp16 → index 0) and confirmed `CP Copy Files to Board` now works — source-level diagnosis held up end-to-end, not just in theory.

### concept: Cursor `.cursor/rules/` discovery in multi-root workspaces is NOT gated by folder order  `evidence-supported`

Prompted by planning a multi-root workspace reorder (moving `ai-persona` away from folder-index 0) — needed to confirm this wouldn't silently stop persona rule injection.

- **Order doesn't gate inclusion.** Cursor scans **every** workspace root independently for `.cursor/rules/` and injects each root's `alwaysApply: true` rules — not just `workspaceFolders[0]`. Evidence (staff-confirmed, Cursor forum, not formal docs — the docs pages don't mention multi-root at all): known **duplication** bugs where the *same* `alwaysApply` rule loads once *per* root (e.g. 6× for 6 git-worktree roots) — that failure mode is only possible if all roots are scanned, which rules out a first-folder-only restriction. Sources: [Bug: always-applied rules duplicated across workspace roots](https://forum.cursor.com/t/bug-report-always-applied-rules-duplicated-across-workspace-roots-in-multi-root-workspaces/151165), [Nested git worktrees load duplicate rules](https://forum.cursor.com/t/nested-git-worktrees-load-duplicate-cursor-rules-into-context-please-dedupe-or-let-us-scope-rule-discovery/163712), [Monorepo rules deduplication](https://forum.cursor.com/t/monorepo-correct-support-and-rules-deduplication/148752).
- **Real (order-independent) multi-root caveat**: a root's `.cursor/rules/` can **silently load none of its rules** if that root mixes flat top-level `.mdc` files with `.mdc` files nested in subdirectories — staff-confirmed bug, no ETA. Source: [Rules from subdirectories not read in multi-root workspace](https://forum.cursor.com/t/rules-from-subdirectories-not-read-in-multi-root-workspace/151107/1). Checked `ai-persona/.cursor/rules/` against this 2026-09-11: clean flat list (`00-…mdc` … `06-…mdc` at top level only; `mandates/`, `memory/`, `reference/` subdirs contain `.md`, never `.mdc`) — **not** affected.
- **Contrast with the `circuitpythonsync` bug above**: that extension *is* genuinely hardcoded to `workspaceFolders[0]` (confirmed from its own source, not inference) — Cursor's own rule discovery is not. Don't conflate the two "first folder" behaviors; one is real, one isn't.
- **Scope**: this is staff-confirmed forum content, not a documented spec — re-verify empirically after any reorder (does the next turn's `<always_applied_workspace_rules>` block still show up?) rather than treating this as permanently settled.

**`circup install <lib>` with no `--path` auto-detects and writes straight to the mounted board** — obvious in hindsight, but caused a confusing "why did this land on the board?" moment 2026-09-11 (exp16) when an agent-run `circup --path <local-repo-root> --board-id … --cpy-version … install asyncio` and a human-run plain `circup install asyncio` happened almost simultaneously, producing byte-identical files on both the local repo and the board within the same second — looked like a hidden auto-sync mechanism at first, wasn't. For local-only staging (git-first workflow), always pass `--path <local-repo-root>` (+ `--board-id`/`--cpy-version` since a plain repo folder has no `boot_out.txt` for auto-detection) — verified in an isolated `/tmp` scratch dir to never touch a mounted board. Logged as ephemeral per Alex — do not invest further investigation unless it recurs.

### concept: `circup` does not pin per-library versions — only whole-bundle snapshots  `evidence-supported`

Prompted by exp16 asking whether the documented `circup install asyncio` recipe (`README.md § Deploy`) precisely restores library versions on a fresh checkout.

- **`circup freeze -r` / `circup install -r requirements.txt` version pins are cosmetic, not enforced.** Read circup 3.0.1's own source (`command_utils.py::libraries_from_requirements`): when reinstalling from a requirements file, it runs `re.split("[<>=~[;]", line)[0]` on every line — i.e. it **strips off everything after any version specifier** and keeps only the bare module name. A committed `requirements.txt` with `asyncio==3.1.1` therefore documents what was on-device at freeze time, but `circup install -r requirements.txt` later will install whatever is **currently "latest"** for the name `asyncio`, not specifically `3.1.1`. Verified by reading the function body directly, not inferred from docs.
- **The real reproducibility knob is the whole-bundle snapshot, not individual libraries.** `circup install` fetches from dated bundle releases (e.g. this session: `adafruit/Adafruit_CircuitPython_Bundle` tag `20260910`, `adafruit/CircuitPython_Community_Bundle` tag `20260911`, `adafruit/circuitpython-fonts` tag `20250418.0.0` — printed as "Using latest bundle for ___" on every invocation). Pin bundles two ways: (a) per-invocation, `--bundle-version <bundle-key>=<tag>` (repeatable flag, format `key=value` like a requirements.txt line); (b) persistently, a `pyproject.toml` with `[tool.circup] bundle-versions = {"<bundle-key>" = "<tag>", ...}` — read by `pyproject_bundle_versions()`, which looks for `pyproject.toml` **only in the current working directory or its immediate parent** (`find_pyproject()`, two levels, not a full upward walk) — so it must sit at (or one level above) wherever `circup` is invoked from. `--bundle-version` on the CLI overrides a pinned `pyproject.toml` value.
- **Practical upshot for a repo that wants "checkout → exact same library versions":** a bare `circup install <lib>` recipe in a README (exp16's current state) is **not** version-reproducible — running it next month pulls whatever's newest in the bundle then. Real reproducibility needs a committed `pyproject.toml` pinning the bundle tag(s) actually used, generated/verified against `circup`'s own "Using latest bundle for ..." output at the time of pinning. A committed `requirements.txt` is still worth keeping as a **human-readable record** of exact per-library versions once installed (`circup freeze -r`), just not as something `circup install -r` will re-enforce on its own.

**See also (cross-domain, not duplicated here):** reading a board's serial console (not flashing) from the agent's own Shell tool hits a *different*, narrowly-scoped sandbox restriction — raw device-file opens (not enumeration, not mounted-volume file reads) need `required_permissions:["all"]`. Directive + exact tested/untested scope: `universal/WORKING_STYLE.md § Workflow & Artifacts` (*Raw device-file I/O needs `required_permissions: ["all"]`…*, 2026-09-11).

### concept: On-device restart/reload mechanisms for CircuitPython test automation  `unverified` (research banked for future autonomous dev-loop design; nothing here is implemented)

Prompted by exp16 Session 19: a one-shot on-device test script (`code.py`) finished and fell back to the REPL before an autonomous serial-log capture could run, because a human chat message's arrival time can't be synchronized to board-execution time. Immediate fix applied was code-shape only (loop the diagnostic script, see `projects/circuitpython-exp16-planetx/SESSION_LOG.md` Session 19) — no device-control capability needed. Alex separately asked to persist the *options analysis* for autonomous restart, since it will matter when designing more autonomous on-device test loops later. Four distinct mechanisms, not to be conflated:

| # | Mechanism | Triggered from | What it needs | Status here |
|---|---|---|---|---|
| 1 | Auto-reload-on-write | Host: any write to a file on the mounted `CIRCUITPY` volume (a `CP Copy Files/Libs to Board`, a raw `cp`, even rewriting an unrelated file like `readme.txt`) | Nothing extra — this is CircuitPython's default behavior (`supervisor.runtime.autoreload`, default `True`; the resulting run reports `supervisor.RunReason.AUTO_RELOAD`) | Always-on side effect, not a tool. **Practical upshot (Alex, 2026-09-11): every individual file-copy operation resets the board — batch multiple file changes into as few sync operations as possible** rather than copying one file, observing, copying another, etc. `concepts/tooling.md`'s existing circuitpythonsync findings (`CP Copy Libs to Board` / `CP Copy Files to Board`) are each one such write. |
| 2 | `supervisor.reload()` | **From within already-running code** on the board (code.py itself, or typed at the REPL) | Code has to already be executing to call it — an external host process cannot invoke this directly without either (a) code.py's own logic deciding to call it, or (b) sending REPL text (= "REPL input", already excluded from the autonomy envelope) | Equivalent to Ctrl-D. Useful as a *self*-triggered restart inside a script's own logic, not as an externally-invoked control. |
| 3 | `supervisor.set_next_code_file(filename, reload_on_success=, reload_on_error=, sticky_on_success=, sticky_on_error=, sticky_on_reload=)` | Called from within currently-running code, takes effect on that run's completion/error | Nothing external — pure on-device chaining | **Most promising lead for a future autonomous multi-stage test loop.** Lets one script hand off to the next (e.g. `stage0.py` → `stage1.py` → `stage2.py` → `stage3.py`) fully on-device, with `reload_on_success=True` skipping the "Code done running, waiting for reload" REPL-wait state entirely — **zero host-triggered resets needed between stages** if all stage scripts are pre-staged on the board at once. Settings live in RAM only; a hard reset/power-cycle reverts to the standard `code.py`/`main.py` search. Source: [`docs.circuitpython.org` `supervisor` module](https://docs.circuitpython.org/en/stable/shared-bindings/supervisor/index.html), corroborated by the original feature PR ([adafruit/circuitpython#3454](https://github.com/adafruit/circuitpython/pull/3454)) and follow-up issue ([#1084](https://github.com/adafruit/circuitpython/issues/1084)). Not yet exercised on this board. |
| 4 | Hardware reset via serial control lines (DTR/RTS toggle, no bytes/content sent) | Host: `pyserial` `Serial.dtr` / `.rts` property writes on the already-open port | A board whose USB interface implements *some* reset-on-control-line behavior | See detailed sub-finding below — **more promising than initially assumed**, but confirmed only for a sibling chip (ESP32-S3), not yet for this board's ESP32-S2. |

**Sub-finding on mechanism 4 (revises an earlier same-session assumption):** the initial hypothesis in `MONITORING.md` was that DTR/RTS-based reset "probably doesn't apply" to native-USB boards like BPI-Bit-S2, reasoning from the classic `esptool` auto-reset circuit (discrete transistors wired to a separate USB-UART bridge chip's DTR/RTS lines, feeding `EN`/`GPIO0` — [esptool boot-mode-selection docs](https://docs.espressif.com/projects/esptool/en/latest/esp32s2/advanced-topics/boot-mode-selection.html)), which BPI-Bit-S2 doesn't have (it uses the SoC's own native USB peripheral, no bridge chip). Follow-up research found this reasoning incomplete: **native-USB ESP32-S3 implements the equivalent reset semantics directly in its own CDC-ACM ROM/firmware, not via external transistors** — confirmed by the chip's own Technical Reference Manual §33.3.2, cited on the [Arduino Forum](https://forum.arduino.cc/t/esp32-reset-at-serial-terminal-shutdown/1391969) (a user quoting the TRM directly, not just forum hearsay):

| RTS | DTR | Action |
|---|---|---|
| 0 | 0 | Clear download-mode flag |
| 0 | 1 | Set download-mode flag |
| 1 | 0 | **Reset the chip** |
| 1 | 1 | No action |

ESP32-S2 and ESP32-S3 share the same native-USB-OTG peripheral family, and this is exactly the mechanism that lets `esptool`/Arduino IDE auto-reset native-USB S2/S3 boards into bootloader mode without a manual BOOT-button press (observed working on other Adafruit ESP32-S2 boards) — so it is **plausible ESP32-S2 implements the same table**, but this has **not** been confirmed against the ESP32-S2 TRM or by an actual on-device trial on BPI-Bit-S2 specifically. Promote to `evidence-supported` only after one of: (a) an ESP32-S2 TRM citation naming the same CDC-ACM RTS/DTR behavior, or (b) a controlled on-device trial (`pyserial`: open the port, toggle `.rts`/`.dtr`, observe whether the board actually resets) — trial (b) is itself a reset action and needs Alex's prior approval before attempting, per the destructive-ops-adjacent caution he asked for around autonomous restarts.

**Why none of this is built yet:** mechanism 3 (on-device chaining) needs no new capability at all and is worth prototyping first, whenever a real multi-stage autonomous loop is wanted — it fully avoids the restart-risk conversation. Mechanism 4 (external hardware reset) would need the TRM/trial confirmation above *and* a capped-budget + approval scheme (Alex's explicit ask: not autonomous at high frequency without caps and prior approval, akin to the `esptool` write/erase carve-out already in `WORKING_STYLE.md`) before any helper script gets built around it. Neither is needed for the current Stage-0 test, which the loop-based `code.py` rewrite already solves without touching any of this.

**How-to-check-status:** re-read this entry before designing any future autonomous multi-board test-loop; if mechanism 3 or 4 gets prototyped, record the outcome here (or promote to a dedicated concept if it graduates past "banked research").
